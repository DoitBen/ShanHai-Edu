## 当前协作机制

- 本项目采用“主 Codex 单入口总控 + 内置子智能体执行 + 项目文档记忆沉淀”的多角色协作模式，当前机制版本为 V0.7 单入口总控。
- 主 Codex 默认身份是产品负责人兼全栈总控：只和用户直接对话，负责把用户需求落地为任务、派发执行、回收结果、组织验收和更新记忆。
- 当前执行团队编制为：3 个前端工程师、3 个后端工程师、1 个测试工程师、1 个系统架构师；同类席位共享同一角色记忆，通过“前端 1 / 前端 2 / 前端 3”“后端 1 / 后端 2 / 后端 3”区分责任范围。
- 当前机制包含 V0.4 总控闭环：重要任务遵循“架构师下发 → 专业角色交付 → 测试工程师验收 → 架构师对照原任务、交付物、测试报告和关键代码/配置 diff 复核 → 通过或再调度”。
- V0.5 起，跨角色重要任务必须先沉淀共同需求文档、契约文档和测试验收文档，再进入 `dispatch.md` 和角色提示词；缺少文档绑定的提示词只能视为临时沟通。
- V0.6 起，重要任务必须区分“代码级完成 / 测试验收通过 / 阶段封板通过”三层状态：执行角色只能声明代码级完成，测试工程师声明测试验收结论，首席系统架构师声明阶段封板结论。
- V0.6 起，涉及普通教师主界面的任务必须有真实浏览器或 DOM 级用户态红线证据；静态契约测试、tsc、lint、build 通过不能单独证明用户态通过。
- V0.6 起，红线返工或封板复测期间存在并行开发冻结区：不得修改当前验收接口字段、页面主流程、provider/storage 行为、状态机和资产状态契约；其他角色只能做不影响当前验收面的文档、调研、Runbook 或隔离 spike。
- V0.7 起，默认不要求用户手动新开多个角色对话；主 Codex 在同一会话中通过内置子智能体派发前端、后端、测试或系统架构师任务，并统一向用户汇报。
- 用户仍可在任意新对话中用自然口令手动指定角色，例如“你是前端工程师”“你是前端开发”“你是系统架构师”“你是产品经理”“你是测试”“你是运维”，但这用于直接查看某角色视角、用户画像体验或重大分歧讨论，不再是默认执行路径。
- 每个角色需要先读取项目级规则、本机制说明、角色调用模板、交付物模板、共享事实、对应角色记忆和最近交接记录。
- 每轮重要工作结束后，需要更新对应角色记忆和交接记录；涉及重要结论、跨角色冲突或阶段推进时，还需要更新决策台账、冲突台账或阶段总控记录。

## 已确认角色

- 主 Codex：产品负责人兼全栈总控，只和用户对话，负责需求落地、任务拆分、子智能体派发、验收复核和记忆沉淀。
- 系统架构师（1 席）：全局统筹、跨角色协调、边界裁决、阶段规划。
- 前端工程师（3 席）：UI/UX 设计、页面体验、交互路径、视觉一致性、前端体验落地。
- 后端工程师（3 席）：后端能力、服务规则、权限安全、稳定性与可维护性。
- 测试工程师（1 席）：业务流程、界面交互、权限角色、边界异常、性能安全等质量验收。
- 产品经理能力：由主 Codex 默认兼任，负责产品定位、网站业务功能、用户价值、市场与用户需求、业务流程、验收标准。
- 运维/部署能力：按专题启用，负责环境变量、密钥注入、容器部署、日志、备份、健康检查和回滚；不实现后端业务接口，不替代测试验收。

## 已确认需求

- 建立“主 Codex 单入口 + 角色记忆 + 项目共享事实 + 交接记录 + 内置子智能体执行”的本地协作模式。
- 支持用户通过“你是某某角色”或自然别名手动指定当前对话角色；但默认由主 Codex 单入口调度，不要求用户手动开多角色对话。
- 保证后续新对话可通过读取角色记忆和交接记录继续接手。
- 建立角色调用模板和交付物模板，降低每次启动和交付的格式漂移。
- 建立决策台账、冲突台账和阶段总控记录，形成可追溯闭环。
- 新增运维/部署工程师作为开发团队固定角色，补齐部署、运行、密钥、日志、备份和回滚职责。
- 前端首屏性能基线：`AppShell` 不静态引入业务大页和 `CommandPalette`，业务 screen 采用 `next/dynamic` 按需加载，命令面板仅打开时挂载。
- 前端设计语言基线：当前采用暖纸白、深青灰、古铜金的教研工作台体系，设计依据以 `docs\FRONTEND_DESIGN.md` 和 `apps\web\src\app\globals.css` 为准。
- 新建项目体验基线：项目创建必须包含角色字典、视觉契约和合规红线，作为 PPT 与导入视频的共同上下文。
- 导入视频产品基线：如果本课需要导入视频，教案中的导入设计必须拆成"导入视频策划卡 + 课堂接入说明"两层；导入视频和教案之间唯一硬连接字段为课程锚点。课程锚点只负责把独立、有吸引力的视频主题自然接回本课学习任务，不负责提前讲解知识点；导入视频不得被教案限制成知识讲解。
- 前端本地真实 API 演示基线：`NEXT_PUBLIC_DEMO_MODE=false` 时，项目列表、创建项目、工作区 manifest、节点详情、`textbook_parse` 生成和确认走后端 API；默认 demo/mock 模式继续隔离使用 mock 数据，不与真实 API 状态混用。
- 架构优化 v2 固定推进顺序：第0周 PPT 主链路 → StateEngine → RuleExecutor → Flywheel → 安全边界；每阶段都先读取仓库 Issues 并修复缺陷，再执行开发、完整测试、提交和推送。
- 第0周 PPT 主链路基线：真实 API runtime manifest 必须包含 `visual_contract`、`character_dict`、`ppt_assembly_plan`、`ppt_page_script`、`ppt_visual_asset`、`pptx_artifact`；`pptx_artifact/generate` 必须写入可下载 PPTX artifact 节点版本；`final_delivery` 暂不进入第 0 周主线。
- Workflow Control Plane Phase 1 基线：质量门禁规则运行时真源为 `storage\control_plane.db`，`workflow\rules\*.yaml` 是 Git 基线和灾备源；新项目创建时绑定 active rule set，旧项目默认不迁移；管理员一期只能治理规则，不允许修改完整 DAG、节点依赖、schema 或状态机。
- T146-T150 本地功能接口门禁已由首席系统架构师裁决为有条件通过：T146 后端 FastAPI 合同、T147 Next 代理/前端契约、T148 浏览器串联初测、T149 前端返工、T150 真实浏览器复测共同支撑；通过范围只限 fake/placeholder + 本地 FastAPI/Next/Web + 浏览器用户态 + 下载代理。T150 已关闭 T148 最终交付普通区红线、PPT/视频回看失效和 duplicate key 阻塞；真实 provider、生产权限、多浏览器、容器冷启动和真实 PPT/视频质量仍需另起专项。
- T150 发现的 `final_delivery` 嵌套导出路径 `/exports/final_delivery/...` 下载 404 已拆为 T151；该问题不阻塞 T146-T150 本地功能接口门禁，但后续若最终交付页要直接提供该路径下载，必须单独修复并复测路径安全。

## 已拒绝或暂不采用

- 暂不采用所有角色在同一对话中无限自由讨论的模式。
- 暂不采用由用户人工新开多个角色对话作为默认执行路径；该方式仅保留为特殊讨论入口。
- 暂不采用无总控的全自动多智能体自由编排；所有子智能体任务必须由主 Codex 明确范围、冻结区、验收标准和交付要求。

- Web 本地开发目录为 `apps\web`，开发启动命令为 `bun run dev`，默认端口 `3000`。

- 真实 provider 演示 Runbook 位于 `docs\ops-real-provider-demo-runbook.md`。
- 真实文本链路由 `PROVIDER_MODE` 控制，真实视频链路由 `VIDEO_PROVIDER_MODE` 控制；推荐完整 E2E 用 `PROVIDER_MODE=real` + `VIDEO_PROVIDER_MODE=placeholder`，真实 Octo 视频单独 smoke。

- 当前后端合成真实多 clip 视频时从 `PATH` 查找 `ffmpeg`，`FFMPEG_PATH` 仍是运维预留变量。

## 统一验收口径

- 用户说出角色身份后，该角色能知道该读取哪些文件。
- 角色能在自己的职责边界内工作，不越权输出。
- 角色工作结束后能更新对应记忆和交接记录。
- 重要结论能进入决策台账。
- 跨角色分歧能进入冲突台账。
- 阶段结束能进入阶段总控记录。
- 新对话读取共享事实、角色记忆和最近交接后，可以继续推进项目。
- 当前管理员规则控制面仅达到本地/内测治理口径：后端 admin API 依赖 `BACKEND_API_TOKEN`，前端本地代理用角色 cookie 做演示级拦截；生产级 JWT/RBAC/session 和用户态 bundle 隔离仍需后续专题验收。
