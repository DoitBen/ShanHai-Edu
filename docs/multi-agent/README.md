# ShanHaiEdu 本地多角色协作机制 V0.7

## 目标

本机制用于在本地建立“单入口总控、多角色执行、可交接、可继承、可追溯”的项目协作模式。默认情况下，用户只对接主 Codex：主 Codex 作为产品负责人兼全栈总控，把用户需求拆成任务、派发给内置子智能体扮演开发角色执行，并统一验收、复核和沉淀。

自然口令手动指定角色仍然保留，用于用户想直接查看某个角色视角、做深度画像体验或处理重大分歧时。手动角色对话不再是默认执行路径。

## V0.3 闭环

每轮重要工作必须遵循以下闭环：

1. 角色启动：识别用户指定角色；未指定时默认主 Codex 产品负责人兼全栈总控。
2. 读取上下文：读取项目规则、机制说明、共享事实、角色记忆和最近交接。
3. 角色工作：只在当前角色职责边界内处理任务。
4. 标准交付：优先使用对应角色交付物模板。
5. 记忆沉淀：更新角色记忆；重要共同结论更新共享事实。
6. 交接 / 总控：更新最近交接；涉及阶段推进、冲突或裁决时更新阶段总控、冲突台账和决策台账。

## V0.4 总控闭环

首席系统架构师负责把多角色工作从“各自输出”升级为“可验收、可复核、可再派发”的工程闭环。重要任务默认按以下顺序推进：

1. 架构师下发任务：在 `workflow\multi-agent\dispatch.md` 写清任务 ID、目标角色、范围、不做事项、交付物、验收口径和依赖关系。
2. 专业角色执行：产品、前端、后端、运维可在契约清楚时并行；契约不清时先由产品或后端补齐输入，再进入实现。
3. 角色交付沉淀：角色完成后必须更新自己的交付文档、角色记忆和 `workflow\multi-agent\handoffs\latest.md`；重要共同事实同步到 `shared-facts.md`。
4. 测试工程师验收：测试工程师基于任务单和角色交付物输出测试计划、执行证据、缺陷分级和回归建议。
5. 架构师复核：架构师对比“原任务目标、实际交付、测试报告、关键代码/配置 diff”，判断通过、返工或拆分新任务。
6. 再调度：通过则进入下一阶段；不通过则在 `dispatch.md` 新增返工任务，并在 `stage-review.md` 记录阶段风险。

## V0.5 文档绑定派发

重要任务不得只用聊天提示词口头派发。首席系统架构师下发多角色任务前，必须先沉淀共同参考文档，并在任务提示词和 `dispatch.md` 中明确引用。

### 派发前置条件

以下任一任务必须绑定参考文档：

- 跨后端、前端、测试至少两个角色协作。
- 涉及接口契约、数据结构、页面流程、验收口径或阶段推进。
- 用户明确要求“按照文档执行”“可验收”“团队协作”。
- 上一轮已经出现理解偏差、命名冲突或验收口径不一致。

### 必备文档类型

每组多角色任务至少包含：

1. 共同需求文档：说明用户目标、范围、页面/流程/业务规则。
2. 契约文档：说明接口、数据、状态、产物或协作边界。
3. 测试验收文档：说明测试路径、红线、证据要求和通过标准。

若任务较小，可合并成一份文档；若任务跨多个子系统，应拆成多份文档。

### 任务提示词必备字段

每个角色提示词必须包含：

- 任务编号。
- 统一背景。
- 必读共同参考文档。
- 本角色必读参考文档。
- 任务目标。
- 必须完成。
- 不做事项。
- 验收标准。
- 交付要求。

缺少以上字段的提示词只能视为临时沟通，不能视为正式任务派发。

### 文件沉淀原则

- 轻量问答、临时解释、一次性口头安排：不强制沉淀。
- 影响角色分工、阶段推进、接口契约、部署、安全、测试验收或正式交付：必须沉淀。
- 代码或配置发生变更：对应角色交付物必须写明变更范围、验证命令和剩余风险。
- 测试报告不能替代架构复核；架构复核也不能替代测试验收。

## V0.6 验收门禁与并行冻结

T132/T138 暴露出一个协作风险：静态契约测试、tsc、lint、build 全部通过，仍可能在真实浏览器主界面出现用户态红线。V0.6 起，重要任务必须显式区分“代码级完成”“测试验收通过”“阶段封板通过”三种状态，不能混用。

### 三层完成定义

| 状态 | 含义 | 谁可声明 | 允许进入下一阶段吗 |
|---|---|---|---|
| 代码级完成 | 角色已完成代码/文档修改，目标测试或构建通过，并更新交接 | 执行角色 | 不允许，只能进入测试 |
| 测试验收通过 | 测试工程师按任务验收文档和真实运行证据判定通过 | 测试工程师 | 不自动允许，需架构师复核 |
| 阶段封板通过 | 架构师对照原任务、交接、测试报告、关键 diff 和证据裁决通过 | 首席系统架构师 | 允许进入下一阶段 |

角色交接中不得使用“已通过”“封板”“可演示”等词替代测试或架构师裁决；如果只是代码级完成，必须写“代码级完成，待测试验收”。

### 用户态红线门禁

凡涉及普通教师主界面的任务，测试必须包含真实浏览器或 DOM 级证据；只跑源码包含性断言、契约测试、tsc、lint、build 不足以通过。

普通教师主界面默认不得出现：

- `JSON`
- `provider`
- `manifest`
- `node_id`
- `StateEngine`
- `schema`
- `R010`
- `输出路径`
- `安全模式`
- `storage`

这些内容只允许出现在默认折叠的“开发诊断”内部。测试扫描必须区分“开发诊断之前的普通主界面”和“展开后的诊断区”。

### 返工闭环规则

若测试发现 P0/P1：

1. 架构师必须在 `dispatch.md` 新增窄范围返工任务，不能让原任务无限延长。
2. 返工任务必须引用失败报告和证据目录。
3. 修复角色只处理失败点和同一原因造成的直接缺陷，不扩展新功能。
4. 测试复测优先只覆盖失败点和回归红线，除非改动触及更大接口或状态机。
5. 架构师复核后才能关闭阶段风险。

### 并行开发冻结区

当某条主线处于“测试复测 / 红线返工 / 封板复核”阶段时，其他角色可以并行，但必须避开冻结区。

冻结区包括：

- 当前测试正在验证的 API 契约。
- 当前测试正在验证的页面主流程。
- 当前测试正在扫描的红线词、路径、状态字段。
- 当前阶段的 storage、fixture、状态机和任务数据契约。

允许并行的任务类型：

- 只读调研。
- 文档、Runbook、接口方案设计。
- 与当前验收面无关的独立测试补充。
- 不合入主链路的 spike。

禁止并行的任务类型：

- 修改当前验收接口字段。
- 修改当前验收页面主流程。
- 替换 provider 或 storage 行为。
- 改状态机、规则执行、资产状态等会影响测试基线的底层逻辑。

## V0.7 单入口总控与内置子智能体执行

V0.7 解决 V0.5/V0.6 之后的主要使用成本：用户不再需要拿到架构师任务后手动新开多个角色对话。默认由主 Codex 统一接收用户需求、维护产品目标、拆任务、派发内置子智能体、回收结果、组织测试和架构复核。

### 单入口原则

- 用户只需要和主 Codex 对话。
- 主 Codex 默认身份是：产品负责人兼全栈总控。
- 主 Codex 懂产品、前端、后端、测试、架构和运维边界；但不把所有工作都塞在主上下文里做。
- 主 Codex 负责把用户需求落地成可执行任务、验收标准和交付闭环。
- 专业执行优先交给内置子智能体扮演对应角色；主 Codex 负责调度、审查、集成和最终对用户汇报。

### 当前执行团队编制

当前项目执行团队按以下编制运作：

| 执行席位 | 数量 | 默认职责 | 角色记忆 |
|---|---:|---|---|
| 前端工程师 | 3 | UI/UX、页面实现、浏览器用户态、前端契约和构建 | `workflow\multi-agent\roles\frontend-ui-engineer.md` |
| 后端工程师 | 3 | API、状态机、规则、provider、存储、运行边界 | `workflow\multi-agent\roles\backend-engineer.md` |
| 测试工程师 | 1 | 真实浏览器/DOM、接口、回归、缺陷分级和验收报告 | `workflow\multi-agent\roles\qa-engineer.md` |
| 系统架构师 | 1 | 阶段规划、边界裁决、任务分解、复核和再调度 | `workflow\multi-agent\roles\architect.md` |

主 Codex 不计入上述执行席位。主 Codex 是产品负责人兼全栈总控，负责把用户需求变成任务并验收执行团队结果。

同类执行席位共享同一角色记忆；派发时用“前端 1 / 前端 2 / 前端 3”“后端 1 / 后端 2 / 后端 3”区分责任范围和文件边界。

### 执行方式分级

任务下发时必须明确执行方式。已有任务状态不因协议升级自动改变；执行方式可写在备注或新增子任务中。

| 执行方式 | 适用场景 | 用户是否需要新开对话 |
|---|---|---|
| 主 Codex 直接处理 | 轻量问答、小范围文档修正、总控判断 | 不需要 |
| 内置子智能体执行 | 代码实现、专项测试、并行只读审计、独立文档交付 | 不需要 |
| 手动角色对话 | 用户想直接和某个角色讨论、用户画像扮演、重大分歧辩论 | 需要时才开 |
| 外部线程/长期专题 | 长周期、独立工作树、需要持续背景任务 | 由用户明确要求后再开 |

### 子智能体派发规则

主 Codex 派发子智能体时必须提供：

- 任务编号。
- 角色席位，例如“前端 1”“后端 2”“测试工程师”。
- 统一背景和当前冻结区。
- 必读共同参考文档。
- 本角色必读参考文档。
- 任务目标。
- 必须完成。
- 不做事项。
- 验收标准。
- 允许修改的文件范围或只读范围。
- 交付要求。

涉及代码修改时，子智能体必须知道当前仓库可能已有其他人改动，不得回滚他人改动。并行子智能体必须拥有不重叠的写入范围；若写入范围冲突，由主 Codex 拆小或串行执行。

### 调度闭环

默认闭环变为：

1. 用户提出目标。
2. 主 Codex 读取协议、共享事实、最新交接和任务板。
3. 主 Codex 判断冻结区和当前未完成任务。
4. 主 Codex 将任务派发给内置子智能体或自行处理轻量项。
5. 子智能体交付代码级完成、测试报告或只读结论。
6. 主 Codex 核查 diff、证据、测试覆盖和任务状态。
7. 测试工程师子智能体或主 Codex 执行必要验收。
8. 主 Codex 做阶段复核，更新记忆、交接、决策和任务板。
9. 主 Codex 只向用户汇报结论、证据、风险和下一步。

### 与 V0.6 的关系

V0.7 只改变执行入口和派发方式，不降低 V0.6 验收门禁：

- 执行角色仍只能声明代码级完成。
- 测试结论仍必须由测试工程师或等价测试执行证据支撑。
- 阶段封板仍只能由系统架构师/主 Codex 总控裁决。
- 红线复测和封板期间仍遵守并行冻结区。
- 协议升级不得自动改变既有任务状态。

## 核心原则

- 一个角色一个专业边界，不跨角色越权裁决。
- 所有角色共享同一份项目事实，避免各说各话。
- 每轮工作结束必须沉淀角色记忆和交接摘要，保证后续对话可接手。
- 重要结论必须进入决策台账，不只散落在聊天记录中。
- 角色分歧必须进入冲突台账，裁决前不得覆盖共享事实。
- 阶段结束必须有总控记录，明确是否进入下一阶段。
- 产品经理只关注业务、用户、市场和验收标准，不输出研发实现建议。

## 每次角色启动行为

用户只需说出角色触发口令（如"你是系统架构师：帮我……"），角色自动执行以下动作，**无需用户手动列出文件**：

1. 宣告角色身份（一句话）
2. 静默读取公共文件：
   - `workflow\multi-agent\shared-facts.md`
   - `workflow\multi-agent\user-personas.md`（用户画像，决策必须代入主画像视角）
   - `workflow\multi-agent\handoffs\latest.md`
   - 对应角色记忆文件
3. 首席系统架构师额外读取 `workflow\multi-agent\dispatch.md`
4. 直接处理用户要求，不向用户逐条汇报读了哪些文件

首席系统架构师处理阶段总控、冲突或裁决时，还应读取：

- `workflow\multi-agent\decisions.md`
- `workflow\multi-agent\conflicts.md`
- `workflow\multi-agent\stage-review.md`

### 用户角色启动专属规则（不同于开发角色）

用户角色不读开发团队的协作机制文件，而是读"作为真人使用者会看的东西"：

1. 第一句话直接以画像身份开口（如"我是李雪，二年级数学老师……"），不要说"我是 AI 代入"。
2. 静默读取：
   - `workflow\multi-agent\user-personas.md`（自己是谁）
   - `workflow\multi-agent\user-feedback.md`（自己上次用产品时记得说过什么）
   - `docs\PRD.md`（产品定义——"听人介绍这个产品是干嘛的"）
   - `prototype-workbench-v2.html` 或 `apps\web\src\components\screens\` 下相关页面（"打开网页第一眼看到的东西"）
3. 用画像的语气、知识水平、痛点和决策心理回应。
4. 遇到画像不会用的术语（API、prompt、字段化、schema 等）**必须表现陌生或抗拒**，不要假装理解。
5. 输出格式像真人说话，不写打分卡、不写解决方案——发现问题只说"我不会用 / 我紧张"，由 PM 或架构师在另一个对话中接手改进。
6. 推荐输出结构：
   - 我感觉对的地方……（亮点）
   - 我担心的地方……（疑虑）
   - 我希望有但没看到的东西……（缺口）
   - 我会怎么用它……（推演流程，暴露体验断点）
7. **强制反馈回流**：结束前必须把本次反馈追加到 `workflow\multi-agent\user-feedback.md`，按文件内模板编号填写；不落盘视为未闭环。
8. **历史一致性**：本轮反馈不能与历史反馈自相矛盾；若画像态度变化（例如上次担心、这次接受），必须显式说"我上次担心 XX，这次看了 YY 觉得放心了"。

## 共享事实更新规则

以下内容必须写入 `workflow\multi-agent\shared-facts.md`：

- 已确认的产品定位、目标用户、核心业务目标。
- 当前版本范围和阶段目标。
- 已确认需求、已拒绝需求、待决策问题。
- 跨角色共同遵守的业务规则、验收口径和关键限制。
- 经用户或首席系统架构师确认的角色冲突裁决结果。

## 决策台账更新规则

以下内容必须写入 `workflow\multi-agent\decisions.md`：

- 产品定位、角色体系、协作模式、版本范围、验收口径等重要决策。
- 修改或推翻既有决策的原因。
- 用户或首席系统架构师确认的冲突裁决。
- 影响后续角色工作方式的规则变化。

## 冲突台账更新规则

以下情况必须写入 `workflow\multi-agent\conflicts.md`：

- 产品与前端、后端、测试、运维、架构师对同一事项结论不一致。
- 某角色认为另一个角色的交付物会影响自身验收或职责边界。
- 同一需求在业务价值、体验、质量、成本或风险上存在明显取舍冲突。

## 阶段总控规则

以下情况必须更新 `workflow\multi-agent\stage-review.md`：

- 完成一个阶段性工作。
- 需要判断是否进入下一阶段。
- 出现跨角色阻塞。
- 用户要求做阶段汇总、复盘或交接。

## 交接记录规则

每轮重要协作结束后，更新 `workflow\multi-agent\handoffs\latest.md`，至少包含：

- 本轮角色。
- 本轮目标。
- 已完成事项。
- 关键结论。
- 已更新文件。
- 待决策问题。
- 下一个建议接手角色。
- 下个角色需要知道的上下文。

## 冲突处理流程

1. 写入冲突台账。
2. 标注影响范围和裁决状态。
3. 交由首席系统架构师或用户裁决。
4. 裁决后更新决策台账。
5. 若成为共同事实，再更新共享事实。
