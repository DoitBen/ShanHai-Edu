# 为什么这样设计

重要设计决策的"为什么"。读这份，能理解每个机制背后的取舍逻辑。

---

## 1. 为什么是函数式 pipeline 契约

### 决策
每个节点定义为 `f(上游 approved 产物, 规范, 种子参数) → 本节点产物`，**禁止读取旁路输入、未 approved 草稿、其他分支同级产物**。

### 为什么
- **可重复性**：同输入永远同输出，便于调试和飞轮分析
- **可降级**：上游变 → 下游自动 needs_review，逻辑明确
- **可解耦**：节点之间没有隐藏依赖，单独可测
- **数学上良定义**：diff、影响分析、增量重生都有清晰边界

### 代价
- 不灵活（用户不能让"第 3 步 PPT 偷偷读第 8 步视频成果")
- 表面上看像约束，实际上是反屎山

### 替代方案
- 自由依赖图（节点间想读什么读什么）— 屎山诱因
- 单向广播（上游推送给下游）— 失去主导权

## 2. 为什么 5 状态 + skipped 而不是更多

### 决策
not_started / drafted / needs_review / approved / blocked / skipped 共 6 个。

### 为什么
- **够用**：覆盖了"开始 / 草稿 / 待审 / 通过 / 阻断 / 跳过"全场景
- **简单**：开发记得住，UI 表达得清晰（不同颜色不同图标）
- **可机器判定**：每个状态的进入/退出条件明确

### 没要的状态
- `partial_done`（部分完成）— 没必要，drafted 就够
- `review_in_progress`（审核中）— v1 单人独立，没必要
- `archived`（归档）— 项目级状态，不污染节点
- `expired`（过期）— 没必要

### 为什么 skipped ≈ approved
- skipped 节点对下游来说视同通过（不阻断 DAG）
- 但语义不同：approved = 用户确认 OK，skipped = 用户主动跳过
- 飞轮分析时要区分（skipped 不进偏好画像）

## 3. 为什么字段化 schema 而不是自由文本

### 决策
所有节点产物结构化字段（JSON Schema 校验），不让 AI 写一段长 Markdown。

### 为什么
- **反幻觉**：自由文本里 AI 可以写任何东西、漏任何东西；字段化强制覆盖
- **可校验**：规则可以逐字段查（"必须有 student_action 字段"），自由文本难
- **可表单化**：前端可按 schema 自动渲染表单，用户改起来直观
- **跨 provider 一致**：DeepSeek/Claude/GPT 都返回同结构 JSON，下游处理代码不变

### 代价
- AI 写起来不"自由"，可能缺少教学法韵味
- prompt 调优需要每节点 × 每 provider 都跑一遍

### 平衡
- 教案是粗粒度（6 字段）：留给 AI 在每段文本里自由发挥
- PPT 页面是细粒度（13 字段）：每个格子都要约束（反幻觉收益最高）
- 视频 v1 简版（必填字段）+ v1.x 攻克：先打通再深度优化

## 4. 为什么连锁失效用方案 A（最简单的"全降级"）

### 决策
上游 current 变更 → 下游所有 approved → needs_review。

### 为什么
- **绝对安全**：永远不会偷偷过期
- **简单实现**：状态引擎逻辑就 1 条规则
- **建立用户信任**：用户敢回头改，因为知道"系统不会暗中放过"

### 不做方案 B/C/D 的原因
- B（用户判定是否影响）：把判断负担给用户，错了责任不清
- C（AI 影响分析）：v1 没有用户基数，AI 判断的准确率没数据支撑
- D（自动 diff 重生）：开发成本是 A 的 10 倍

### 升级触发条件
等真听到用户喊"改个错别字也要全审太烦"，再上 B/C/D。
**不等抱怨就升级 = 过度设计**。

## 5. 为什么 SQLite + 文件系统而不是直接 PostgreSQL

### 决策
v1 每个项目独立 SQLite + 同目录的 assets/。

### 为什么
- **零部署成本**：内部用户 docker-compose up 就能跑
- **朴素感**：用户可以打开文件管理器看到自己的项目
- **可备份**：zip 一个目录 = 完整可移植项目
- **schema 可平迁**：将来上 PostgreSQL，schema 改少量即可
- **每项目独立**：跨项目零耦合，磁盘空间也好管理

### 不直接上 PostgreSQL 的原因
- 内部部署增加运维成本
- 单机性能足够，没并发压力
- 数据导入导出要走 SQL 工具

### v1.x → 云端时
- SQLite schema → PostgreSQL schema（结构基本不变）
- assets/ → 对象存储（S3 / 阿里云 OSS）
- 代码层因为 ProjectStore 抽象，业务逻辑不动

## 6. 为什么多 provider 而不是 ZB 一个 LLM

### 决策
教案/文稿用 DeepSeek、监督用 Claude、通用用 GPT、生图用 gpt-image-2、视频用 omni_flash-10s。

### 为什么
- **不同模型擅长不同事**：DeepSeek 中文好且便宜、Claude 推理强、GPT 稳
- **抗单点故障**：一家挂了能切到 fallback
- **成本可调**：贵的（Claude）只在监督用，便宜的（DeepSeek）跑大量生成
- **用户透明**：UI 上显示用了哪个模型，用户可改

### 代价
- prompt 跨 provider 适配的开发量大
- 每节点要维护 default + fallback 两套测试
- 调试时要排查"是 prompt 问题还是 provider 问题"

### 不做的事
- 不做自家 fine-tune（v1 没数据）
- 不做模型路由智能优化（v1 用人工配置就够）

## 7. 为什么逐页审查智能体（PPT 节点专属）

### 决策
PPT 第 3 步每生成一页立刻让 Claude 按规则审查，不合格自动重生。

### 为什么
- **避免灾难**："做完 12 页才发现整体不对" → 全部推倒重做
- **提质**：每页都过机器审一遍，质量底线高
- **隐性传递判断标准**：审查规则本身就是教研团队的判断显性化

### 为什么只在 PPT 节点
- PPT 是用户说的"最硬的骨头"
- 教案、文稿等节点产物形态简单，规则 builtin 检查够
- v1 先验证 PPT 节点上效果，再考虑推广

### 为什么不强制 hard_block
- 用户有绝对主导权
- override 行为本身是飞轮信号（"哪条规则被这位用户最常 override"）

## 8. 为什么飞轮是核心商业资产

### 决策
- 不训练模型，但全量采集偏好数据（approved 版本 / 编辑 diff / override / 反馈）
- 重做时检索注入 few-shot
- 偏好画像可视化让用户感知

### 为什么
- **用户粘性的源头**：用得越久越懂用户 = 不愿换工具
- **数据壁垒**：竞品挖团队挖不走（数据在 SQLite 里）
- **冷启动后的指数曲线**：第一次草稿一般，第十次草稿超预期
- **可演进**：v1 用 few-shot、v2 上 fine-tune、v3 做客户层私有模型

### 关键设计
- approve 后又改了什么 比 哪一版被 approve 更有价值（后者只是偏好方向，前者是精修信号）
- 上完课反馈 比 课件到手反馈 更有价值（前者是效果信号）
- 飞轮可视化对用户必须可感知（否则黏性体感不到）

## 9. 为什么角色字典是合规底线

### 决策
- 必须细粒度字段（多视角 + 服装锁定 + 发型 + 体型 + 风格约束）
- banned_keywords 必须包含 ["真人", "photorealistic", "real child"]，**不可删除**
- 风格只能是 cartoon / silhouette / 3d_non_realistic

### 为什么
- **肖像权风险规避**：AI 生图模型可能生成真人脸，角色字典锁死非写实风格 = 法务保护
- **视觉一致性**：跨 PPT / 视频两条分支，角色长得一样
- **跨节点引用**：character_id 在多处出现，schema 强约束让引用可靠

### 用户的关键洞察
> "约定死了这个角色的各个描述，就不会侵权了"

这是工程化解决合规的典范——把法务问题变成 schema 约束。

## 10. 为什么红线规则用 hard_block 不给 override

### 决策
6 条红线（中文男声 / 禁英文 / 单段不算完整 / 角色禁真人 / 候选不冒充终版 / 数学进可编辑层）严格阻断，无 override 入口。

### 为什么
- **事故防复发**：这 6 条都是吃过亏的（事故复盘里都有记录）
- **合规底线**：肖像权、版权、消费者保护
- **品牌信用**：用户花钱买产品，不能因为某次 override 出事故砸招牌

### 为什么不"软警告"
- 软警告意味着用户可以选择忽略
- 用户在赶时间时容易忽略警告
- 一次事故的代价远高于"少几次强制阻断带来的不爽"

### 用户的绝对主导权与红线的关系
- 主导权 = 用户在合规范围内的全自由
- 红线 = 不可被绕过的边界
- 这两者不冲突，是"自由"和"宪法"的关系

## 11. 为什么 workflow.yaml 是状态机真源

### 决策
不在代码里硬编码 9 步流程，状态引擎读 workflow.yaml 动态构建 DAG。

### 为什么
- **修改成本低**：改流程改 yaml 即可，不改代码、不编译、不重新部署
- **产品和教学法可参与**：教学法负责人能看懂 yaml，能提改动
- **配置即文档**：yaml 自身就是流程文档
- **避免硬编码屎山**：原 14 份规范的悲剧就是因为每改一次需求改 3 处文档

### 代价
- 调度器代码复杂度上升
- yaml 校验要做（防写错）

### 关键约束
- workflow.yaml 改动必须走 PR（产品 + 教学法 review）
- CI 必须跑 yaml schema 校验

## 12. 为什么不做"反复横跳"

### 决策
v1 强制线性 9 步，不支持"走到第 5 步又回去改第 2 步" 的自由跳转。

### 为什么
- **用户明确拒绝**："学习成本高，教研员搞不定"
- **保持产品形态简单**：教程能讲清
- **不破坏函数式 pipeline 契约**：上游变了下游全降级，跳着改会让降级链路混乱

### 关键区别
- **横跳** = 已经走到第 5 步又回去改第 2 步（v1 不支持）
- **回头修改** = 当前停在第 5 步，主动回到第 2 步编辑（v1 支持，触发连锁失效）
- **冷启动输入** = 第 0 步上传参考 PPT 作风格锚点（v1 支持，是表单字段不是横跳）

后两者属于线性流程的一部分，不破坏 DAG。

## 13. 为什么视频 v1 用最简版

### 决策
L1/L2/L3 视频 schema 设计完整版，但 v1 只用必填字段。

### 为什么
- **MVP 边界**：端到端跑通优先，单点深度推后
- **视频是 token 大头**：每段视频几块钱，6 段就是几十块。先把流程跑顺，再优化质量
- **用户明确说**："视频我们后期再攻克。先把整个链路打通。"

### v1 简版的成本
- 视频质量没那么震撼
- 但能跑通整个链路 = 用户可以拿到完整成品
- 比"PPT 极致但视频根本没接"好

### v1.x 攻克项
- prompt 自动拼装器
- 景别 / 运动 / 多层元素清单
- 节奏分配
- 情绪基调
- 数学元素显隐控制

## 14. 为什么反馈在用户第二次使用时弹窗

### 决策
- 课件到手反馈：交付完成时弹（次品）
- 上完课反馈：用户**第二次进产品做新项目时**弹（主品）

### 为什么第二次使用而不是当时
- 当时弹 = 打断使用流程（用户刚拿到课件想下载就走）
- 当时填的反馈是"质量观感"，不是"课堂效果"
- 第二次回来 = 用户已经用过这节课了 = 有真实反馈
- 第二次回来 = 用户对产品有粘性 = 反馈率更高

### 用户的判断
> "可以就是在教师第二次使用我们的软件的时候。做第二套教案 PPT 的时候，我们可以有一个弹窗，就是让他填写一个反馈。"

简洁、精确、自然。

## 15. 为什么不做 AI 味专项治理

### 决策
v1 不做"去 AI 味"机制，留长期风险。

### 为什么
- **飞轮自然减轻**：用户改得越多，AI 越接近用户风格
- **去 AI 味方案是独立项目**：rewrite + 多模型轮换 + 高频词剔除，工作量大
- **v1 数据不够**：判断"什么是 AI 味"需要用户基数和编辑信号
- **触发条件未到**：还没听到用户说"看着像 AI 写的"

### v1 唯一动作
飞轮设计要鼓励"用户改 AI 的版本"而不是"用户接受 AI 的版本"——
前者沉淀去 AI 味信号，后者沉淀 AI 味本身。

### 何时启动
- 用户基数 > 100 且
- 单用户使用 > 10 节课 且
- 课后反馈出现"看着像 AI" 关键词

## 总结：这些设计决策的共同特征

1. **第一性出发**：每条决策可回溯到 4 条第一性原理
2. **反屎山倾向**：每条决策都警惕"现在便宜但未来贵"
3. **可演进设计**：v1 最简、留升级口、不破坏旧数据
4. **用户主导但有红线**：自由在合规范围内
5. **飞轮优先**：所有决策考虑"这能不能产生数据信号"
6. **现实主义**：承认 AI 不能做某些事（教学法判断、合规判断、震撼力的最终判定）

这些特征本身就是产品的隐性资产。下一次设计决策时回看这份，能保持判断一致性。
