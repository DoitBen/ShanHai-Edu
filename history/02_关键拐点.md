# 关键拐点

讨论过程中几个改变方向的瞬间。每个拐点都是"如果当时换一个回答，产品会完全不同"的点。

---

## 拐点 1：用户拒绝"反复横跳"

### 发生时刻
2026-06-18 22:00 左右

### 问题
我提出 4 个待澄清问题，其中包括"用户怎么思考——按线性 9 步 vs 反复横跳"。

### 用户回答
> "用户怎么思考，我们尽量将线性的9步做到极致完美。这些修改反复横跳是需要长期沉淀的。并且需要有教程的，不是一时半会就能搞定的，开发了用户估计都不太熟练。"

### 影响
- 排除了"灵活的非线性工作流"路线
- 9 步硬性串联成为基础设施
- 不做 diff 预览 / 影响范围分析 / 批量应用（推到 v2/v3）
- 教程系统独立成产品的另一部分商业

### 如果走另一条路
- 产品形态会变成 Notion / Coda 那种自由编辑的画布
- 学习成本极高，教研员上不了手
- 商业模式也会完全不同（卖灵活性 vs 卖工业化质量）

---

## 拐点 2：从"打回-改"到"重做-编辑双通道"

### 发生时刻
2026-06-18 21:00 左右

### 问题
我假设的"审核通过 / 打回修改"机制。

### 用户回答
> "然后审核不是打回，而是重做，很快的。就是谁在做这个项目，他对这个项目有绝对的主导权，他可以直接编辑得到的产物，以及让 AI 重做这个节点的产物，直到用户觉得满意为止。"

### 影响
- "绝对主导权"成为核心产品原则
- 没有"打回意见"这种结构化输入（用户不写反馈，直接重做）
- 飞轮信号变成"用户在第几版 approve + approve 后又改了什么"
- 编辑器要支持直接改 Markdown / 字段，不只是 review

### 如果走另一条路
- "打回意见"会成为飞轮的主要信号源
- 但用户不愿意每次写反馈（"重做更快"）
- 飞轮收集到的数据会有偏（嘴上说的 ≠ 实际接受的）

---

## 拐点 3：用户揭穿"屎山"

### 发生时刻
2026-06-19 00:00 左右

### 问题
我刚写完 PRD v2（775 行），自我感觉良好。

### 用户回答
> "现在你回头看看我们的这个工作流，他是不是不符合半自动化？而且冗余信息很多。好多都是感觉是屎山堆起来的？对吗？"

### 影响
- 触发了对原 14 份规范的深度反思
- 识别出"prompt 工程时代的产物 vs 半自动化产品需要的输入"差异
- 进入完全重构阶段
- 从 14 份 → 5 份 → 75 个文件的三层契约

### 如果走另一条路
- 我会继续按 PRD 推动开发
- 开发拿到 14 份矛盾的规范 + 一份漂亮的 PRD
- 半年后代码里嵌满"特殊情况处理"，屎山搬进生产环境

### 用户为什么能问出这个
- 因为已经吃过"屎山堆起来不能改"的亏（原工作流就是教训）
- 因为已经定义了"对外开放产品"的标准（不是内部凑合）

## 拐点 4：用户要求"血能流通"

### 发生时刻
2026-06-19 00:30 左右

### 问题
我刚写完 5 份纯净规范集，又自我感觉良好。

### 用户回答
> "我说的是这个能不能直接串联作为整个工作流的参考基线。是否是血？可以注入流通的？"

### 影响
- 触发了"规范集 ≠ 可执行基线"的认识
- 要求做 JSON Schema / workflow.yaml / 真实规则 YAML / 真 prompt
- 产品有了机器可直接消费的层

### 如果走另一条路
- 开发拿到 5 份 Markdown，自己派生 JSON Schema 等工程文件
- 但派生过程会丢失语义、容易写歪
- 不同开发可能派生出不同 schema，产品最终又裂开

## 拐点 5：用户对 PPT 字段数量的判断

### 发生时刻
2026-06-18 22:30 左右

### 问题
我问"PPT 13 字段全做 vs 先做 5 个关键字段"。

### 用户回答
> "都做吧。反正 PPT 不消耗 token。"

### 影响
- PPT 字段化走最细粒度
- 反幻觉机制有了最强抓手
- 后端建表、前端表单、prompt 约束三层都有结构化输入

### 关键洞察
"PPT 不消耗 token"——这一句话区分了两种成本：
- **结构定义的成本**（schema 字段数）：写一次永久使用，边际成本几乎零
- **内容生成的成本**（token）：每次调用都花钱

用户准确识别了这两种成本不一样，所以可以在结构上大方、在内容上节约。

## 拐点 6：用户对视频的态度

### 发生时刻
2026-06-18 23:45 左右

### 问题
我问"视频字段化跟谁对齐：粗粒度像教案，还是细粒度像 PPT"。

### 用户回答
> "这个生成视频这一块是一个大头，是我们最期待解决的一个问题。"

> （但稍后又说）"视频我们后期再攻克。先把整个链路打通。"

### 影响
- 视频被定位为"最难 + 最有商业价值 + 但 v1 先打通链路"
- L1/L2/L3 视频 schema 设计了完整版，但 v1 只用必填字段
- v1.x 攻克路径明确（节奏 / 情绪 / 景别 / 运动 / prompt 自动拼装器）

### 反映的产品思维
"端到端跑通"优先于"某一节点深度"。
这是成熟产品经理的判断——MVP 不是"做一两个功能极好"，是"全流程都能跑"。

## 拐点 7：用户对合规问题的破局

### 发生时刻
2026-06-18 23:00 左右

### 问题
我担心生图模型出现真人未成年人会有肖像权问题。

### 用户回答
> "合规面不是很重要。主要是这个我们生成视频的时候，他存在约束，比如这个视频画面 omni 他不能出现真人孩子未成年等肖像的。但是这有合理的手段可以保证避开这个点（就是使用多立体图，前后左右、脸部等等的专门特写，我们约定死了这个角色的各个描述，就不会侵权了）"

### 影响
- 角色字典从"普通模块"升级为"合规底线"
- 多视角描述 + 服装锁定 + 风格非写实约束 = 合规保护
- v1 必须细粒度做角色字典

### 反映的洞察
用户已经从实战中找到了"AI 生图 + 合规"的工程化解法。这不是法务的事，是产品设计的事。

## 拐点 8：用户拒绝"做标杆课例"

### 发生时刻
2026-06-18 23:15 左右

### 问题
我建议产品里内置 3-5 个完整跑完的标杆课例，让用户第一次看到震撼力。

### 用户回答
> "这个细节1就是标杆课例由谁做这个东西，我们不需要我们直接对外开放，因为我们做的就是老师。我们这边有很多大量用户，老师他都是我们团队的。我们团队可以先打磨，所以说这个先不急，我们先做一个 MVP。"

### 影响
- 标杆课例从 v1 推到 v1.x
- v1 范围进一步收窄
- 内部教研团队自己用 = 自带样板 = 不需要预设样板

### 反映的判断
用户清楚自己的资源结构：有团队、有老师、有真实用户。
不需要假装"已经有完美样本"才上线。
内部用、内部打磨、内部产生样本 = 自然的冷启动路径。

---

## 总结：用户的产品判断风格

通过这 8 个拐点能看出用户的判断特征：

1. **拒绝过度设计**：能简化的就简化（"反复横跳是 v2 的事"）
2. **资源现实主义**：清楚自己有什么没什么（"团队就是老师"、"合规靠工程化"）
3. **MVP 优先**：端到端 > 局部深度
4. **识别成本结构**："PPT 不消耗 token" 这种洞察
5. **不容忍屎山**：主动揭穿、要求重构
6. **要求可消费**："血能流通吗"
7. **接受不确定**：视频 v1 简版、v1.x 攻克
8. **绝对主导权信念**：审核 = 重做，不是打回

这些判断风格本身就是产品的隐性资产。下一个产品决策时回看这些拐点，能保持判断一致性。
