# ShanHaiEdu v1 下一阶段产品范围

版本：2026-06-24
任务：T005
角色：产品经理能力
状态：作为 T006-T009 的共同产品输入，待主 Codex / 系统架构师集成

## 1. 产品目标

v1 下一阶段只服务主画像 P01 李雪老师：一名准备区级公开课、时间紧、压力大、追求作品感、抗拒 AI 味的小学数学骨干教师。

本阶段的业务目标不是展示一个完整技术工作流，而是让李雪老师围绕一节公开课拿到可试讲的完整作品包：

- 教案：有公开课结构、课堂追问、重难点和数学准确性检查点。
- PPT：按 40 分钟课堂组织成 12-16 页左右，每页能看出教师讲什么、学生做什么、数学内容是什么。
- 导入视频：45-60 秒优先，服务开课前情境导入；必须是独立、有吸引力的短片，最后通过课程锚点接回课堂，不提前讲解知识点。
- 逐页讲稿和检查清单：让她能把剩余时间用于磨课、试讲和教研组反馈修改。

对 P01 来说，产品成功不是“AI 生成了一堆内容”，而是“今晚或几天内能交出一套我敢拿去给教研组看的 70 分以上成品，并且我知道每一步怎么确认、怎么改”。

## 2. P01 场景

### 2.1 标准公开课场景

李雪老师 28-30 天后要上区级公开课，例如二年级数学《万以内加法（一次进位）》。她白天正常上课和管班，每晚只有 1-2 小时备课。她希望按线性流程完成：

1. 创建公开课项目，填写教材、课题、班级基础、公开课要求和课堂风格。
2. 第一晚拿到完整教学流程和多个导入方向，先确认大方向。
3. 第二晚生成 PPT 草稿，逐页检查讲法、学生动作、板书和数学内容。
4. 第三晚确认导入视频脚本、首帧和合规边界，再生成视频。
5. 后续根据教研组反馈局部修改，不推倒重来。
6. 最终下载教案、PPT、导入视频、逐页讲稿和修改记录。

### 2.2 一晚应急场景

李雪老师只有一晚上准备初稿，明天上午教研组就要看。产品必须支持“快速成品优先”的体验预期：

- 5 分钟内完成关键项目资料填写。
- 先给一版可直接试讲的教学流程，不只给漂亮空话。
- PPT 成品页必须覆盖导入、问题情境、操作探究、竖式讲解、易错提醒、练习和板书总结。
- 视频先给 3 个导入脚本标题和第一帧方向，让她选一个再继续。
- 完成一晚应急流程后，应能查看或下载“明天可试讲包”，即使不是最终 90 分版本，也要可讲、可改、可下载。

### 2.3 反馈来源要求

本阶段必须消费并回应以下 P01 反馈：

- `F-P01-001`：产品要按公开课备课流程给出完整作品，用户一关一关看懂、确认、再进入下一步。
- `F-P01-002`：产品必须围绕真实公开课压力，支持教案、PPT、导入视频和试讲修改记录的完整帮助。
- `F-P01-003`：只剩一晚时需要快速生成可试讲成品，尤其要明确视频时长、画风、配音、合规、数学点、预览确认和局部重做。

## 3. 功能边界

### 3.1 登录

业务目标：让李雪老师以“我能继续我的公开课项目”的心智进入产品，而不是进入技术系统。

范围内：

- 登录后回到项目首页。
- 显示当前身份和最近项目，不要求她理解账号体系。
- 演示或本地内测场景下，登录入口必须避免暴露密钥、provider、API 等技术概念。
- 登录失败或权限不足时，用教师能理解的话说明下一步，例如“请联系项目管理员开通访问”，不展示技术错误。

验收标准：

- P01 能从登录进入首页，并看到自己可继续处理的公开课项目。
- 普通界面不出现 `API`、`provider`、`token`、`schema` 等技术词。
- 登录不是 v1 的卖点，不在本阶段扩展复杂组织、班级、区域管理。

### 3.2 首页

业务目标：让李雪老师快速判断“我的公开课做到哪一步、下一步该点哪里、今晚能不能继续推进”。

范围内：

- 展示进行中的公开课项目。
- 项目卡片至少表达：课题、年级教材、当前备课阶段、进度、下一步动作、最近更新时间。
- 提供明确的新建项目入口。
- 已完成或归档项目可以弱展示，但不得干扰当前公开课推进。
- 首页语言必须面向教师，例如“继续生成公开课教案”“查看 PPT 草稿”，不得显示工作流节点、工程状态或数据来源。

验收标准：

- P01 不需要打开工作区，就能知道下一步要做什么。
- 首页不得把本地 API、manifest、节点数量、数据来源、storage 路径作为普通信息展示。
- 首页项目进度必须与工作区用户态步骤一致，不能首页显示已完成而工作区仍未解锁。

### 3.3 新建项目第 0 步

业务目标：用最少理解成本收集一节公开课的核心上下文，并把合规、视觉一致性和作品目标提前锁住。

范围内：

- 教材与课题：学科、年级、教材版本、册次、课题、课型、课时长度。
- 公开课目标：公开课级别、使用场景、剩余准备时间、希望风格、班级基础。
- 教材来源：从教材库选择或上传新教材；用户先确认教材范围，再回填项目字段。
- 角色字典：默认卡通或插画风，不允许真人感未成年人，不要求用户写复杂提示词。
- 视觉契约：PPT 与导入视频共用的主配色、风格关键词和画面气质。
- 合规红线：不生成真人儿童脸、不用真实课堂实拍感、不提前讲解知识点、数学内容必须可检查。
- 导入视频偏好：是否需要视频、期望时长、视频类型标签、配音偏好、是否优先快速成品。
- PPT 偏好：页数范围、结构模板、视觉丰富度、是否需要逐页讲稿。

业务流程：

1. 选择教材来源。
2. 选择目录章节或课时知识点。
3. 系统回填教材字段，用户确认或微调。
4. 填写公开课目标和班级情况。
5. 确认角色字典、视觉契约和合规红线。
6. 确认 PPT / 导入视频偏好。
7. 创建项目并进入工作区“教材内容”或“教案生成”阶段。

验收标准：

- P01 能在 5 分钟内完成一晚应急项目的关键资料填写。
- 第 0 步不出现输出路径、安全模式、API、provider 等技术配置。
- 角色字典、视觉契约和合规红线是项目共同上下文，后续 PPT 与导入视频都必须遵守。
- “课程锚点”作为导入视频与教案之间的唯一硬连接进入项目上下文。

### 3.4 工作区

业务目标：把工作区从工程调试台改成公开课备课工作台，让李雪老师按“看结果 -> 改一改 -> 确认下一步”完成作品。

用户态步骤：

1. 项目信息。
2. 教材内容。
3. 教案生成。
4. 导入视频方案。
5. PPT 草稿。
6. 视频生成。
7. 最终交付。

范围内：

- 顶部只展示用户态步骤：已完成、当前步骤、未解锁。
- 当前步骤只保留一个主任务卡，说明这一步要完成什么、现在要做什么、当前系统结果、可编辑区域、生成依据和主按钮。
- 主按钮按状态变化：生成草稿、保存修改、确认并进入下一步、查看下一步。
- 已完成步骤可回看，默认只读；修改已完成步骤前必须提示会影响哪些后续材料。
- 未解锁步骤不得展示空结果、技术错误或依赖失败，只说明应先完成哪一步。
- 教案必须以 Markdown 编辑和预览方式展示，不让普通用户编辑结构化原始内容。
- PPT 草稿必须让用户逐页看讲法、学生动作、画面内容、数学内容和板书提示。
- 导入视频方案必须先展示候选脚本标题、课程锚点、第一帧方向和合规提示，再进入生成。
- 视频结果必须支持按镜头查看旁白、画面和数学点；不合适时优先局部重做，不要求整段重来。
- 开发诊断可以保留，但默认折叠，且不得影响普通教师主界面。

导入视频业务边界：

- 导入视频是独立创意短片，不是把教案开头拍成视频。
- 导入视频不得提前讲本课定义、方法、结论或完整探究步骤。
- 导入视频与教案的唯一硬连接是课程锚点。
- 视频必须避免真人感未成年人、真实儿童脸和真实课堂实拍感。
- P01 默认偏好中文自然男声、语速稳定、卡通或插画风、生活化数学场景。

验收标准：

- P01 在任意当前步骤都能回答：我现在看什么、改什么、点什么进入下一步。
- 普通教师主界面不出现 `JSON`、`provider`、`manifest`、`node_id`、`StateEngine`、`schema`、`R010`、`输出路径`、`安全模式`、`storage`。
- 已完成步骤能回看，未解锁步骤不能误入。
- 教材内容、教案、导入视频方案、PPT 草稿命名清楚，不混用。
- 用户态红线专项 T140/T141 已封板的范围继续保持，但不得扩大解释为真实 provider 或全链路通过。

### 3.5 反馈飞轮

业务目标：让产品越用越贴近李雪老师，而不是每节课都从零开始。

范围内：

- 课件到手反馈：最终交付后询问这套材料是否能试讲、最需要改哪里。
- 下次使用反馈：第二次创建项目时回访上一节课使用效果。
- 过程信号：记录用户在哪一步重做、最终确认哪一版、确认后手动改了哪些内容、哪些审查提示被忽略或覆盖。
- 用户可见偏好摘要：用教师能理解的标签表达系统学到的偏好，例如“更喜欢生活情境导入”“PPT 希望每页有明确学生动作”“视频更偏卡通男声旁白”。

验收标准：

- 反馈入口不打断当前成品生成主流程。
- 反馈问题不使用 prompt、schema、模型等术语。
- 飞轮结论必须可被用户理解和纠正，不能变成隐藏黑盒。

## 4. 暂不纳入范围

本阶段不纳入以下内容，避免把当前专项封板误解为完整 v1 上线：

- 真实 provider 全链路验收，包括真实 Minimax、真实图片生成、真实视频生成、真实 TTS。
- 真实视频主链路封板，包括多镜头生成、配音、字幕、拼接、局部重做和最终 MP4 质量验收。
- PPT 主链路封板，包括真实 PPTX 生成、逐页审查、视觉资产生成和下载成品验收。
- 生产级权限、JWT/RBAC/session、多租户、用户态 bundle 隔离。
- 多浏览器兼容、移动端适配、性能压测。
- 任意教材泛化、全教材库后台、教材版本后台治理。
- SaaS、区域教研员批量管理、多人协作、评论审批、组织看板。
- 教程系统、复杂高级配置、模型成本控制面板。
- AI 味专项治理、fine-tune、跨用户偏好复用。
- dispatch 状态变更、阶段封板裁决和上线宣布。

当前已封板范围仅限 T138/T139 用户态红线专项：普通教师主界面不暴露指定工程红线词、开发诊断默认折叠、教材页段入口不暴露本地路径。它不代表真实 provider、生产权限、任意教材泛化、多浏览器、真实视频或 PPT 主链路通过。

## 5. 跨角色共同验收标准

### 5.1 前端体验验收

- 登录、首页、第 0 步、工作区和反馈入口使用教师语言，不使用技术语言。
- 首页能明确呈现项目进度和下一步动作。
- 第 0 步能完成教材、公开课目标、角色字典、视觉契约、合规红线、PPT / 视频偏好。
- 工作区只暴露用户态步骤，不把后端节点当主导航。
- 每个当前步骤有唯一主按钮，已完成可回看，未解锁不能进入。
- 普通主界面红线词扫描继续为零命中，开发诊断默认折叠。

### 5.2 后端支撑边界验收

- 后端支撑的业务数据必须能让前端表达用户态步骤、当前状态、已完成回看、未解锁原因和下一步动作。
- 后端输出给普通用户的错误必须能转译为“发生了什么、用户能做什么”，不能只剩技术原因。
- 真实 provider、权限、生产环境、视频和 PPT 主链路若未验收，必须在对外状态中保持未完成或待验证，不得被产品文案包装成已通过。

### 5.3 测试验收

- 测试必须覆盖 P01 标准公开课场景和一晚应急场景。
- 测试必须包含真实浏览器或 DOM 级证据，不能只看源码、接口或构建结果。
- 测试报告必须区分：用户态红线专项通过、产品主流程通过、真实 provider 通过、生产权限通过、多浏览器通过。
- 任一普通界面出现红线词、技术路径、技术错误直出，均不得判定用户态通过。
