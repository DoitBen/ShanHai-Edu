# T007 前端产品形态差距审查

日期：2026-06-24
角色：前端 1 子智能体
范围：首页、新建项目、工作区、前端 workflow 映射、已有浏览器红线证据
结论口径：只输出差距报告和最小改造建议，不做 UI 代码实现，不改变任务状态。

## 1. 审查结论

当前前端已经从“节点调试台”明显收敛成教师可理解的备课工作台：新建项目按教材来源、知识点、项目信息、视频偏好、PPT 模板 5 步推进；工作区普通主界面按 7 个用户态步骤呈现；T140 浏览器复测已证明工作区教材内容主界面不再暴露 `JSON/provider/manifest/node_id/StateEngine/schema/R010/输出路径/安全模式/storage`，教材页段 PDF 入口也已走后端代理。

但它还没有完全对齐 PRD v1 的“线性 9 步双分支公开课生产链”。当前最大差距不是单个组件样式，而是产品口径存在三层映射：PRD 的 9 步、`workflow.ts` 的 14 节点、工作区的 7 步用户态聚合。这需要主 Codex/产品负责人先确认统一口径，再安排前端最小改造和 T009 测试计划。

- `apps\web\src\components\screens\NewProjectScreen.tsx`：当前新建项目实现。
- `apps\web\src\components\screens\ProjectWorkspaceScreen.tsx`：当前工作区实现。

## 3. 当前前端实际产品形态

### 3.1 首页

首页以“继续工作”为主视觉入口，包含项目概览、待处理事项和系统轻状态。真实 API 模式下项目列表不使用 demo mock 数据，待办事项为空并提示“真实 API 模式下待办事项需等待任务接口接入”。系统轻状态仍来自 `MOCK_SYSTEM_STATUS`，主要展示调度器、队列任务、存储使用和最近心跳。

已对齐点：
- 首页主任务明确：继续最近项目或新建项目。
- 项目卡能显示当前阶段、进度和下一步动作。
- T139 后加载态已从工程表达改为“正在同步项目列表”。

仍有差距：
- “待处理事项”真实 API 模式尚未接真实任务/待办接口，用户反馈飞轮也没有在首页形成可见入口。
- 系统轻状态仍偏平台运行视角，对 P01 老师价值有限，容易抢占普通教师注意力。

### 3.2 创建项目

当前新建项目是 5 步：

1. 选择教材来源。
2. 选择课时知识点。
3. 项目信息。
4. 导入视频偏好。
5. PPT 草稿模板。

已经落地的用户态能力：
- 教材库下拉展示“人教版 / 小学数学 / 一年级 / 上册”这类用户可懂格式。
- 知识点来自后端解析结果，支持教材页段、教材内容、核心知识点、教案参考等弹窗/抽屉。
- 视频关键词支持标签多选和自定义，预计时长支持下拉和自定义。
- PPT 结构使用固定模板下拉。
- 第 3 步包含角色字典描述、角色安全规则、视觉风格关键词和合规红线，并说明它们会作为 PPT 与导入视频共同上下文。
- 普通新建页已隐藏输出路径、安全模式、provider 等技术字段。

差距：
- PRD 的第 0 步要求“项目配置 + 角色字典 + 视觉契约”是第一屏/项目级必填契约；当前角色字典、视觉契约、合规红线位于第 3 步，且更像文本说明和草稿字段，不是强结构化契约。
- PRD 要求角色字典细粒度字段，如角色 ID、多视角描述、服装锁定、发型锁定、体型比例、非写实风格、禁用关键词、参考图；当前前端只提供合并文本域，后续难以稳定供 PPT 资产和视频资产引用。
- PRD 的产品红线“中文旁白、禁英文配音、禁真人感未成年人、多分镜终版、候选不冒充终版”当前主要以合规文本框承载，缺少锁定值/不可关闭的清单式呈现。

### 3.3 工作区

当前工作区普通主界面是 7 个用户态步骤：

1. 项目信息。
2. 教材内容。
3. 教案生成。
4. 导入视频方案。
5. PPT 草稿。
6. 视频生成。
7. 最终交付。

这 7 步通过 `USER_WORKSPACE_STEPS` 聚合底层节点：
- 项目信息：`project-meta`、`project-config`、`visual-contract`、`character-dict`。
- 教材内容：`textbook-parse`。
- 教案生成：`open-lesson-plan`。
- 导入视频方案：`video-design-import`。
- PPT 草稿：`ppt-plan`、`ppt-script`、`ppt-assets`、`pptx-generation`。
- 视频生成：`video-script`、`video-screenplay`、`video-assets`、`storyboard`、`video-generation`。
- 最终交付：`final-delivery`。

已对齐点：
- 普通主界面不再直接展示后端 manifest 节点。
- 当前步骤有“目标 / 你现在需要做什么 / 当前结果 / 依据 / 主按钮”的任务卡。
- 已完成步骤可回看，未解锁步骤不进入详情。
- 教材内容已改为教师可读卡片。
- 开发诊断默认折叠，T140 浏览器扫描通过。
- 导入视频方案已经突出课程锚点，并提示后续脚本会沿用。
- 视频生成结果页对 fake/placeholder/真实 provider 失败有一定区分，例如“当前只证明已创建视频生成任务和 clip 记录，不承诺真实成片质量”“真实视频服务暂不可用”。
- PPTX artifact 已有生成与下载入口。

差距：
- PRD 9 步双分支里 PPT 分支应从第 1.5 步后并行推进，第 2/3/4A/7 步具有逐页脚本、视觉资产、PPTX 门禁含义；当前 7 步把它们压成“PPT 草稿”，对用户可理解性提升明显，但弱化了逐页审查、数学准确性和视觉资产门禁。
- 视频分支 PRD 要求第 4B/4C/5B/6/8 逐层推进，包含首帧审核、逐镜头生成、拼接前验收；当前“视频生成”聚合了文稿、分场、资产、分镜、最终视频，容易让用户以为一步就能产出终版视频。
- `workflow.ts` 仍定义 14 个前端节点，并包含 `lesson-plan-final` 这类 PRD 9 步里没有明确单列的节点；真实 API 又曾只返回 MVP 节点。三套口径未形成统一映射表，后续测试和文案容易漂移。
- 工作区仍保留 demo 专属视频方案、证据预览 mock 内容和系统轻状态 mock；虽然多数在 demo 或诊断场景，但在 T009 计划中必须明确扫描范围。

### 3.4 PPT / 视频 / 教材 / 教案分支呈现

教材：新建项目阶段支持教材库、上传、切分/解析、知识点选择和证据包；工作区教材内容以课时标题、教材页码、知识点摘要、解析状态、教材依据和 Markdown 预览呈现。

教案：工作区教案生成支持 Markdown 编辑/预览、保存和确认。PRD 要求教案 6 字段与三类九套导入设计结构化，当前 UI 已可显示教案和导入方案，但不是完整字段化编辑器。

导入视频：当前有导入视频方案、课程锚点确认、视频文稿/剧本/资产/分镜摘要、视频生成任务和 MP4 下载入口。PRD 要求导入视频保持独立创意，只通过课程锚点回接课堂；当前已经有课程锚点展示和校验，但“首帧先审再视频”“逐镜头拼接前验收”仍未成为普通主界面的显性关卡。

PPT：当前新建项目有 PPT 风格、页数、结构模板；工作区有 PPT 草稿聚合步骤和 PPTX artifact 下载入口。PRD 要求 PPT 总装、13 字段逐页脚本、PPT 视觉资产、ppt-master/PPTX 生成分步可审；当前普通 UI 仍偏聚合摘要，后续若进入 PPT 主链路，必须拆出更明确的逐页检查体验。

### 3.5 demo/mock 模式 vs 真实 API 模式

当前前端已经做了隔离：真实 API 模式项目列表、创建项目、manifest、节点详情和部分写链路走后端；demo 模式使用 mock 数据。页面中也存在多处提示，如“当前为 demo 模式，真实教材解析需切换到真实 API 模式”“演示模式不导出真实 PPT，请切换真实 API 模式”“真实 API 模式下待办事项需等待任务接口接入”。

用户理解风险：
- P01 老师不理解 demo、API、mock 这些词。虽然 V0.6 红线主要约束工作区普通区，但首页和新建项目仍可能出现“真实 API 模式 / demo 模式”这类工程词。它们对测试和开发有用，但对普通教师不是产品语言。
- fake/placeholder 视频链路目前能演示“任务创建、clip 状态、占位 MP4”，但如果文案不持续强调“只代表本地演示”，用户容易误解为真实视频能力已完整通过。
- 真实 API 模式下仍有若干“待接接口”的提示，这对工程师透明，但对教师用户应转换成“暂未开放 / 该步骤稍后支持”的产品语言。

### 3.6 用户反馈入口 / 飞轮

机制文件已经存在：`workflow\multi-agent\user-feedback.md` 定义用户反馈台账、反馈分类、PM 消费规则和飞轮闭环；PRD 也把“课件到手反馈”和“上完课反馈”作为核心商业资产。

前端可见状态：
- `ProjectWorkspaceScreen.tsx` 已有 `feedbackOpen`、`feedbackDraft`、`submitDeliveryFeedback()`、交付反馈弹窗相关实现。
- 但首页、新建项目和工作区常规流程里，反馈飞轮不是稳定、显眼、可解释的用户功能；它更像最终交付区域里的局部入口和团队机制文件，而不是产品主线的一部分。
- “上完课反馈”“第二次使用弹窗”“偏好画像可视化”尚未在当前前端产品形态中形成可见闭环。

## 5. 最小改造建议

### P0：统一前端流程口径，避免 T009 无法验收

建议先由主 Codex/产品负责人裁决并输出一张固定映射表：PRD 9 步、前端 7 步用户态、底层节点/后端 manifest 节点之间如何对应。前端后续只按这张表调整文案和测试选择器，不直接重构工作流。

触及红线封板面：会触及工作区普通主流程文案和步骤映射，必须由测试工程师补 T140 同类浏览器红线扫描。
可安全排期内容：只新增文档/映射说明、不改 UI 时不触及封板面。

### P0：把 demo/API/mock 词从普通教师路径替换为产品语言

建议普通教师路径使用“演示数据 / 已连接后端 / 暂未开放 / 本地演示视频 / 真实视频服务暂不可用”这类语言，保留工程词到开发诊断或管理员环境。特别是首页空状态、新建项目教材解析提示、工作区待接接口提示。

触及红线封板面：会触及首页、新建项目、工作区文案；工作区需复扫红线词。
可安全排期内容：先列文案替换清单和测试断言，不改功能。

### P1：第 0 步角色字典/视觉契约/合规红线改成结构化摘要 + 锁定项

建议不大改新建流程，只在第 3 步内把三块从“文本域为主”升级为最小结构化卡片：
- 角色：角色名、身份、风格、服装/发型、禁真人关键词。
- 视觉：主配色、风格关键词、字体偏好。
- 合规：中文旁白、禁英文配音、禁真实未成年人、多分镜终版、候选不冒充终版，以不可关闭清单展示。

触及红线封板面：主要触及新建项目，不直接触及 T140 工作区红线，但 T009 应覆盖新建项目截图。
可安全排期内容：先只调整信息结构和保存字段映射，不接 provider。

### P1：PPT 草稿聚合步骤补“逐页检查入口”提示

建议保留 7 步大框架，但在 PPT 草稿任务卡内明确拆出“结构方案 / 逐页脚本 / 视觉资产 / PPTX 下载”的子状态；不要马上做完整富编辑器。这样能对齐 PRD 13 字段逐页脚本和 PPT 视觉资产要求，也能给 T009 明确测试点。

触及红线封板面：触及工作区 PPT 步骤，需浏览器用户态复测。
可安全排期内容：若只补报告和测试计划，不触及 UI。

### P1：视频生成聚合步骤补“首帧审核 / 分镜验收 / 局部重试”口径

建议在视频生成任务卡中把当前已有 clip 状态、单 clip 刷新/重试、MP4 下载能力，包装成用户可懂的三段：先看画面、再生成片段、最后验收拼接。短期不用实现真实首帧工作流，但不能让“生成视频”看起来等同一键终版。

触及红线封板面：触及工作区视频步骤，需浏览器用户态复测。
上线前风险：真实 provider、真实视频、TTS、拼接质量未由 T140 覆盖，不能宣称通过。

### P2：让反馈飞轮成为可见产品能力

建议先在最终交付步骤内固定展示“课件到手反馈”入口，并在首页或项目卡加入“上次反馈/待课后反馈”的轻量提示；偏好画像可后置。当前机制文件已有反馈台账，但教师用户在前端还感知不到“越用越懂我”。

触及红线封板面：最终交付区变更需复测；首页轻提示不触及 T140 红线面但需 T009 覆盖。

### P2：减少首页系统轻状态对普通教师的干扰

建议普通教师默认隐藏或弱化“调度器 / 队列 / 存储 / 心跳”，管理员再显示更完整运行状态。P01 老师关心的是“我下一步做什么、材料是否生成、是否能下载”，不是运行监控。

触及红线封板面：不直接触及工作区红线，但影响首页体验。

## 6. 给 T009 的测试计划输入

T009 不应只重跑 T140 红线；建议至少覆盖：

1. 首页真实 API 模式：继续工作、项目概览、待办空态、系统轻状态是否使用教师可懂语言。
2. 新建项目：5 步流程、教材库下拉、知识点选择、教材证据包弹窗、视频标签、PPT 模板、第 0 步角色/视觉/合规信息是否可见。
3. 工作区：7 步用户态导航、已完成回看、未解锁 toast、教材内容、教案 Markdown、导入视频方案课程锚点、PPT 草稿、视频生成、最终交付。
4. 红线扫描：普通主界面开发诊断之前不得出现工程红线词；扫描范围应包含新建项目和工作区，首页另做产品语言扫描。
5. demo/真实模式理解：普通教师路径不得把 demo/mock/API/provider 当作核心解释；开发诊断或管理员区域可以保留。
6. 反馈入口：最终交付反馈弹窗是否可见、可提交失败态是否可懂、是否有后续飞轮提示。
7. 剩余风险声明：真实 provider、真实视频、PPT 主链路、多浏览器、生产权限不应由 T140 结论替代。

## 7. 建议主 Codex 集成方式
