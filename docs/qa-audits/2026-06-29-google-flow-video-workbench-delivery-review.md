# Google Flow 视频工作台交付级审查与整改建议

> 审查日期：2026-06-29  
> 审查对象：`feat/google-flow-core-video-workbench`（PR #25，head `e1299adb`）  
> 目标：将现有视频工作流从“核心闭环可用”提升至“可稳定交付、可排障、可扩展”。

## 1. 审查结论

当前实现已经完成多参考图上传与排序、提示词生成、异步任务轮询、历史记录、失败重试、视频回存和真实 Omni smoke，核心闭环已经成立。

但当前版本仍不建议直接作为交付级版本发布。主要风险集中在：

1. 轮询 Effect 可能因状态更新反复重启，形成高频同步请求。
2. 正式工作台仍位于“开发诊断”折叠区，不是用户正式入口。
3. 并发同步缺少任务锁和单调状态约束，可能状态倒退或重复下载。
4. 幂等请求存在数据库竞态，可能把合法重试返回为 500。
5. 服务异常退出后，任务可能永久停留在 `submitting`。
6. 上游原始响应和临时签名 URL 被持久化，超过最小数据保存范围。
7. 重试缺少后端状态限制和重复计费确认。
8. 用户错误提示、触屏交互、视频有效性验证及运维监控尚不完整。

建议设置三个门槛：

- **合并门槛**：修复全部 P0 项并完成对应自动化测试。
- **试运行门槛**：完成关键交互、错误恢复、限流和监控。
- **正式交付门槛**：完成 CI 门禁、容量验证、存储治理和回滚演练。

## 3. P0：合并前必须处理

### P0-1 轮询可能形成请求风暴

**涉及文件**

- `apps/web/src/components/video-workflow/use-video-workflow-polling.ts`
- `apps/web/src/components/video-workflow/VideoWorkflowWorkbench.tsx`

轮询 Effect 依赖活动任务数组及调用方传入的内联 `syncRun`。同步成功更新 Zustand 中的 runs 后，会触发重新渲染、依赖变化和 Effect 重启；Effect 重启后立即同步，可能绕过 4 秒轮询间隔。

**整改要求**

1. 同步函数使用稳定引用，或由 Hook 直接读取稳定 store action。
2. 使用单次 `setTimeout` 调度下一轮，避免 `setInterval` 重叠。
3. 增加单飞锁，上一轮同步未结束前不得开始下一轮。
4. 失败时指数退避并加入随机抖动，成功后恢复正常间隔。
5. 页面隐藏或离线时暂停轮询，恢复后立即同步一次。
6. 服务端设置同一任务的最小同步间隔。

**验收标准**

- Fake Timer 证明首次同步一次，随后严格按间隔执行。
- 慢请求期间没有重叠同步。
- 普通组件重渲染不会重启轮询周期。
- E2E 对同步请求总数设置上限。

### P0-2 正式工作台入口错误

**涉及文件**

- `apps/web/src/components/screens/ProjectWorkspaceScreen.tsx`
- `apps/web/e2e/video-workbench.spec.ts`

当前工作台挂载在“开发诊断”折叠区的“运行”标签中，浏览器测试也需要先展开开发诊断。

**整改要求**

1. 将 `VideoWorkflowWorkbench` 挂载到项目工作区正式的视频生成任务区域。
2. 开发诊断只保留原始状态、响应摘要、链路 ID 和调试操作。
3. 正式入口设置独立错误边界，不影响项目其他功能。
4. 桌面端使用三栏布局，手机端使用“素材、创作、历史”标签切换。

**验收标准**

- 用户无需打开开发诊断即可完成上传、生成、等待、播放和下载。
- E2E 从正式项目工作区入口开始。
- 诊断面板不可用时，正式视频功能仍可工作。

### P0-3 并发同步可能状态倒退或重复下载

**涉及文件**

- `apps/api/app/video_workflow.py` 的 `sync_run`

多个同步请求可以同时查询和写入同一任务。较慢的 `processing` 响应可能覆盖已经写入的 `completed`；两个完成请求也可能同时写同一个临时 MP4。

**整改要求**

1. 引入任务级互斥锁或数据库租约。
2. 定义单调状态转换表，禁止终态回退。
3. 下载使用唯一临时文件名，成功后原子替换。
4. 锁内重新读取最新状态，已下载时直接返回。
5. 保存 Provider 更新时间或状态版本，拒绝旧响应覆盖新状态。
6. 下载失败只更新 `download_status`，不得将生成状态改回 `failed`。

**验收标准**

- 两个并发同步请求只触发一次下载。
- 乱序返回 `completed -> processing` 时最终仍为 `completed`。
- 不产生残缺视频或共享临时文件竞争。

### P0-4 幂等创建存在竞态

**涉及文件**

- `apps/api/app/store.py`
- `apps/api/app/video_workflow.py` 的 `create_run`

当前采用“先查询、再插入”。并发相同 `client_request_id` 可能同时查询为空，其中一个插入时触发唯一键异常并返回 500。

**整改要求**

1. 捕获唯一约束异常并回滚事务。
2. 按 `project_id + task_type + client_request_id` 重新读取任务。
3. 请求快照一致时返回已有任务。
4. 快照不一致时返回 409 `IDEMPOTENCY_CONFLICT`。
5. Provider 提交增加领取或租约，保证只有一个工作者执行外部提交。

**验收标准**

- 20 个并发相同请求返回同一 `run_id`。
- Provider `submit_video` 只执行一次。
- 相同幂等键、不同参数稳定返回 409。

### P0-5 `submitting` 状态缺少崩溃恢复

本地任务创建后、Provider task ID 持久化前，服务可能退出。此时任务没有 Provider ID，现有同步逻辑无法继续。

**整改要求**

1. 保存 `submission_started_at`、`submission_attempt` 和租约到期时间。
2. 无 Provider ID 且提交超时的任务转为 `submission_unknown`。
3. 禁止自动再次向 Provider 提交，避免重复扣费。
4. 用户确认后才能创建重试任务，并保存 `retry_of_run_id`。
5. 后台恢复任务扫描过期租约并写入可解释状态。

### P0-6 上游原始响应与临时 URL 不应持久化

**涉及文件**

- `apps/api/app/providers.py`
- `apps/api/app/video_workflow.py`

Provider 当前返回 `raw` 和 `video_url`，随后可能被合并进任务结果。临时签名 URL 不应进入数据库、备份或普通日志。

**允许持久化的字段**

- Provider task ID
- 内部标准状态和进度
- Provider 更新时间
- 脱敏错误码和有限长度错误摘要
- 下载状态、文件相对路径、字节数和校验值

`video_url` 只在当前同步请求内用于下载；`raw` 只允许进入受控、脱敏、限时保留的服务端调试日志。

## 4. P1：试运行前必须处理

### P1-1 后端限制重试状态

- `failed`：允许创建新任务。
- `submission_unknown`：必须携带 `confirm_possible_duplicate=true`。
- `completed + download_failed`：只重试原任务下载，不重新生成。
- `submitting/queued/processing/completed`：返回 409。

### P1-2 Provider 就绪状态必须真实

配置接口应返回：

- `provider_ready`
- `reason_code`
- `user_message`
- 支持的模型、尺寸、时长和参考图数量

进入 real 模式但缺少 API Key 时，前端必须禁用提交并明确显示“服务端尚未配置密钥”。

### P1-3 建立内部状态枚举边界

Provider 的 `pending`、`submitted`、`running`、`in_progress`、`success`、`succeeded` 必须全部映射为内部固定枚举。未知状态不得直接透传前端，应记录脱敏摘要并进行有限次数轮询。

### P1-4 错误提示分层

API 错误应包含：

- `code`：稳定机器错误码。
- `message`：面向用户的中文说明。
- `retryable`：能否安全重试。
- `action`：建议动作。
- `trace_id`：支持人员排查使用。

普通 Toast 不直接展示内部错误码。轮询错误不得静默吞掉，应显示连接状态、下一次重试时间和手动重试入口。

### P1-5 上传交互完善

每个文件独立显示等待、进度、成功、格式错误、大小超限、图片损坏和网络失败。批量上传允许部分成功。拖拽使用独立且可聚焦的手柄，并支持键盘排序。触屏删除不能依赖 hover。

### P1-6 视频文件与播放器验证

服务端至少验证：

1. Content-Type 白名单。
2. 最大下载大小和下载超时。
3. 文件非空且包含 MP4 `ftyp` 标识。
4. 可选使用 ffprobe 验证容器、时长和媒体流。
5. 保存 SHA-256、字节数和媒体元数据。

播放器需要覆盖加载中、解码失败、文件不存在、重新加载、重新下载和下载源文件。E2E 应使用真实可播放的小型 MP4，等待 `loadedmetadata` 并断言 `duration > 0`。

### P1-7 草稿、项目切换和费用保护

1. 提示词与参考图选择按项目保存草稿。
2. `projectId` 变化时清除旧项目临时状态。
3. 默认每个项目只允许一个活动视频任务。
4. 创建第二个活动任务前明确确认。
5. 服务端增加用户、项目和 Provider 级限流与配额。

## 5. P2：正式交付前完成

### P2-1 素材清单并发安全

JSON manifest 的读改写在并发上传、删除时可能丢失更新。交付版本建议将素材元数据迁移到数据库表，文件系统只保存二进制内容。

### P2-2 存储生命周期治理

必须定义项目配额、用户配额、临时文件清理、软删除保留期、失败任务清理、备份恢复、对象存储迁移和 CDN 策略。

### P2-3 可观测性

至少采集 Provider 提交成功率和延迟、排队时间、生成时间、下载时间、同步次数、退避次数、错误码、重试率、疑似重复提交、视频下载字节数和存储增长速度。

日志必须包含 `project_id`、`run_id`、`trace_id`，不得包含密钥、Authorization、完整签名 URL 或未经脱敏的 Provider 响应。

### P2-4 CI 与分支保护

GitHub Actions 至少执行：

1. API 单元测试和并发测试。
2. TypeScript 类型检查。
3. ESLint 和生产构建。
4. 前后端契约测试。
5. Playwright 正式入口测试。
6. Secret 和依赖漏洞扫描。
7. 迁移与启动冒烟测试。

真实 Omni smoke 应在 staging 手工或定时执行，不在普通 PR 中消耗真实额度。

### P2-5 部署拓扑验证

如果浏览器跨域直连 API，CORS 必须允许 DELETE 等实际方法；如果统一经 Next 服务端代理，应在架构文档中明确，并通过部署环境 E2E 验证。

## 6. 自动化测试补充清单

### 后端

- 20 个并发幂等创建请求返回同一 run，Provider 只提交一次。
- 并发同步乱序返回时状态不倒退，只下载一次。
- 提交崩溃后租约超时进入 `submission_unknown`。
- 活动任务和完成任务禁止重新生成。
- Provider 状态别名完整映射。
- 下载内容类型、大小、MP4 魔数、超时和中断测试。
- 素材并发上传与删除不丢数据。
- 跨项目资产、任务和文件访问全部隔离。

### 前端

- 轮询频率、单飞和退避 Fake Timer 测试。
- 正式入口无需打开开发诊断。
- 上传部分失败和单文件重试。
- `submission_unknown` 重复费用确认。
- Provider 未配置时的明确提示。
- 项目切换不保留其他项目选择。
- 触屏删除、键盘排序和焦点可见性。
- 视频 `loadedmetadata`、播放失败和重新加载。

### 端到端

- 文生视频和 1 至 7 张参考图路径。
- 第 8 张参考图被阻止并明确提示。
- 页面刷新后恢复运行中的任务。
- 网络短暂断开后自动恢复。
- 有效 MP4 可以加载元数据、播放和下载。
- 双击生成不会创建两个任务。
- 两个浏览器标签页同时打开同一项目时状态一致。

## 7. 推荐实施顺序

### 第一批：可靠性阻断项

1. 修复轮询调度。
2. 将工作台移至正式入口。
3. 实现任务锁、单调状态机和下载单飞。
4. 修复幂等竞态。
5. 实现提交租约和崩溃恢复。
6. 清理 Provider 持久化字段。

### 第二批：交互与安全

1. 统一错误协议和用户提示。
2. 限制重试并增加重复计费确认。
3. 完善上传、拖拽、触屏和草稿体验。
4. 验证 MP4 并完善播放器异常状态。
5. 增加限流、配额和活动任务限制。

### 第三批：交付工程

1. CI 和分支保护。
2. 指标、日志和告警。
3. 素材数据库化与存储治理。
4. 部署拓扑、容量、备份和回滚演练。
5. Staging 真实 Omni 连续稳定性验证。

## 8. 发布准入标准

- 所有 P0 项关闭并有自动化回归测试。
- 正式入口完成核心闭环，开发诊断不是必经路径。
- 并发情况下没有重复 Provider 提交、状态倒退或重复下载。
- 崩溃恢复不会造成任务永久卡死或静默重复扣费。
- 用户能够理解并处理上传、提交、轮询、生成、下载和播放错误。
- 真实 MP4 经过服务端验证并在浏览器中完成可播放性验收。
- GitHub 合并门禁、监控告警、限流配额和存储清理已启用。
- Staging 完成连续真实 Omni 验证，报告不包含敏感信息。
- 发布、回滚、数据恢复和 Provider 故障降级流程已经演练。
